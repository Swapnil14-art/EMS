# EMS (Event Management System) - Master Project Context & Deep System Behavior
> This is the single source of truth for AI-centric development. It describes the backend API architecture, database integrity, process flows, failure points, and tight role-based guardrails of the EMS project.

---

## 1. System Architecture & Tech Stack

### Frontend Architecture
*   **Framework:** Next.js (React)
*   **UI/UX:** Component-based architecture utilizing React Hooks and custom Contexts for state management.
*   **Routing Structure:** Role-based routing directories. Access is gated at the page/layout level with specific user-based layouts.
    *   `SidebarLayout.tsx` handles left-navigation based on role.
    *   Profile dropdown handles user-specific settings.
*   **Networking:** Axios or native `fetch` wrappers mapped to backend endpoints, attaching `Bearer` JWT tokens generated by login.

### Backend Architecture
*   **Framework:** FastAPI (Python 3.x)
*   **Server:** Uvicorn running synchronously or asynchronously depending on deployment; typically bound to `0.0.0.0:8000`.
*   **Database Integration:** 
    *   **Engine:** SQLAlchemy with Async (`asyncpg`).
    *   **Validation:** Pydantic V2 schemas for I/O validation.
*   **Dependency Injection:** `get_db` yields DB session. `get_current_user` extracts JWT. `require_roles` checks matrix.
*   **Configuration State:** `app/config.py` uses `BaseSettings` reading from `.env`. Injecting fake config can break SMTP or database bindings.

### Asynchronous Jobs (Celery)
*   **Broker:** Redis (usually `redis://localhost:6379/0`).
*   **Scheduler:** `celerybeat-schedule` manages time-based Cron triggers.
*   **Worker Threads:** Manage email dispatches, Word DOCX generation, and time-based status upgrades.

## 4. API Endpoint Contract Matrix

### /auth Router
*   `POST /auth/login` → Returns JWT.
*   `GET /auth/me` → Returns User context.
*   `POST /auth/change-password` → Modifies `hashed_password`.

### /events Router
*   `POST /events/` → Creates event in `draft`.
*   `GET /events/` → Lists events (Students see filtered).
*   `PUT /events/{id}` → Edits event (Fails if not draft).
*   `DELETE /events/{id}` → Deletes (Fails if not draft).
*   `POST /events/{id}/submit` → Pushes from draft to workflow.
*   `POST /events/{id}/upload-poster` → Maps `poster_path`.
*   `POST /events/{id}/upload-participant-doc` → Maps `participant_doc_path`.
*   `POST /events/{id}/upload-sponsor` → Appends to `EventSponsor` list.

### /registrations Router
*   `POST /registrations/{event_id}/register` → Creates DB relation. Checks deadlines.
*   `DELETE /registrations/{event_id}/cancel` → Updates relation to `cancelled`.
*   `GET /registrations/my` → Lists student's personal bookings.

### /approvals Router
*   `GET /approvals/pending` → Lists events pending for current user's role/department.
*   `POST /approvals/{event_id}/action` → Dispatches to `approval_service`.

### /reports Router
*   `POST /reports/{event_id}/submit` → Generates report schema, archives event.
*   `POST /reports/{event_id}/upload-photos` → Requires at least 1 file.
*   `GET /reports/{event_id}/generate` → Downs DOCX binary blob.

### /dashboard Router
*   `GET /dashboard/admin` → Global sums.
*   `GET /dashboard/associate_dean` → Department sums.
*   `GET /dashboard/coordinator` → Club sums.

## 5. Event Lifecycle Transitions (Step-by-Step)

1.  **Draft Config:** Coordinator POSTs `/events/`. Status = `draft`.
2.  **Submit Event:** Coordinator POSTs `/events/{id}/submit`. 
    *   If standard: Status → `pending_associate_dean`.
    *   If collaborative: Status → `pending_coordinator_parallel`.
3.  **Parallel Gate (If Collab):** All coords hit `/approvals/{id}/action` (approve). Status → `pending_associate_dean`.
4.  **Dean Gate:** Dean hits `/approvals/{id}/action` (approve). Status → `pending_director`.
5.  **Director Gate:** Director hits `/approvals/{id}/action` (approve). Status → `approved`.
6.  **Time Gate 1 [START]:** Celery reads `start_datetime`. Status → `ongoing`.
7.  **Time Gate 2 [END]:** Celery reads `end_datetime`. Status → `completed`.
8.  **Report Gate:** Coord POSTs `/reports/{id}/submit`. Status → `archived`.

## 6. Key Backend Services

### `approval_service.py`
Determines next-stage routing based on action payload.
* If `action == rejected` → Global Reject. Email sent.
* If `action == suggested_changes` → Status flags to `suggested_changes`. Email sent.
* Evaluates `collaborative` group counts explicitly block-by-block.

### `venue_clash_service.py`
Verifies overlaps.
* Overlap logic: `eventA.start < eventB.end AND eventA.end > eventB.start`.
* Only factors events that are `approved` or `ongoing`.
* Can be bypassed manually by Dean/Director with `override_reason` string.

### `storage_service.py`
Disk writing.
* Paths: `<STORAGE_ROOT>/events/<id>/<type>/<filename>.ext`
* Protects against blob bloat by deleting prior posters if a new one is uploaded.

## 14. Edge Case Scenarios (CRITICAL)

### 1. Event Edited During Approval
*   **Scenario:** A coordinator realizes a typo and tries to PUT a new payload while Dean is reviewing.
*   **System Response:** FastAPI halts at router. `if event.status != "draft": raise 403`. 
*   **Resolution:** Coordinator cannot edit. They must request Dean to use "Suggest Changes" action to bounce it back to editing mode.

### 2. Event Edited After Approval
*   **Scenario:** Event is fully `approved`, but the venue changed.
*   **System Response:** System blocks Coordinator entirely. 
*   **Resolution:** ONLY `super_admin` role bypasses the status lock. An admin must intercept and manually patch the JSON payload via their overrides.

### 3. Event Cancelled Mid-Approval
*   **Scenario:** Coordinator wants to junk an event that Director is currently reviewing.
*   **System Response:** System blocks DELETE operation because `status != 'draft'`. 
*   **Resolution:** The Director must Reject the event, moving it to an end-state, from where it sits dormant.

### 4. Collaborative Approval Partial Success/Failure
*   **Scenario:** Club A, B, and C are collaborating. C decides to Reject.
*   **System Response:** The single Reject action instantly transitions the global event to `rejected`. The approvals of A and B evaporate contextually.
*   **Resolution:** Club A must create a new draft or edit the event and resubmit from scratch.

### 5. Missing Documents
*   **Scenario:** Coordinator tries to submit Report without uploading a photo.
*   **System Response:** `reports.py` router specifically executes `os.listdir()` on the photo directory. If length is 0, HTTP 400 is raised. 

### 6. Time Conflicts Generation
*   **Scenario:** A draft event overlaps time with an already approved event.
*   **System Response:** Submitting for approval triggers `check_venue_clash`. System errors out with HTTP 400.
*   **Resolution:** The Dean can physically bypass this constraint by supplying a `venue_clash_override_reason` payload string during their approval step.

### 7. Invalid Date Inputs
*   **Scenario:** End Date is before Start Date during draft creation.
*   **System Response:** Pydantic validation intercept or custom router validator throws 422 Unprocessable Entity.

### 8. Duplicate Actions
*   **Scenario:** Student clicks Register 5 times extremely quickly.
*   **System Response:** Database throws IntegrityError on `event_registrations` table due to `UNIQUE(event_id, student_id)`. FastAPI catches and returns standard 409 Conflict.

### 9. Unauthorized Access Attempts
*   **Scenario:** Coordinator manually types the Admin Dashboard `/dashboard/admin` endpoint URL.
*   **System Response:** `require_roles("super_admin", "director")` fails. Throws HTTP 403. Frontend Sidebar layout logic masks the button.

### 10. Report Override
*   **Scenario:** Event lacked structured data. Admin uploads a pre-made PDF.
*   **System Response:** System uses alternative `/reports/{id}/upload-doc` which creates a phantom `EventReport` record with 0-value fields simply to force the status to `archived`.

## 15. State Transition Matrix

STATUS → POSSIBLE NEXT STATUS → TRIGGER → ROLE RESPONSIBLE

*   **draft** → `pending_associate_dean` → *submit_event()* → `club_coordinator`
*   **draft** → `pending_coordinator_parallel` → *submit_event()* (Collab) → `club_coordinator`
*   **pending_coordinator_parallel** → `pending_associate_dean` → *action(approve) x ALL* → `club_coordinator`
*   **pending_coordinator_parallel** → `rejected` → *action(reject) x 1* → `club_coordinator`
*   **pending_associate_dean** → `pending_director` → *action(approve)* → `associate_dean`
*   **pending_associate_dean** → `suggested_changes` → *action(suggest_changes)* → `associate_dean`
*   **pending_associate_dean** → `rejected` → *action(reject)* → `associate_dean`
*   **pending_director** → `approved` → *action(approve)* → `director`
*   **pending_director** → `suggested_changes` → *action(suggest_changes)* → `director`
*   **pending_director** → `rejected` → *action(reject)* → `director`
*   **suggested_changes** → `pending_associate_dean` → *submit_event()* → `club_coordinator`
*   **approved** → `ongoing` → *Celery Beat (Time)* → `System`
*   **ongoing** → `completed` → *Celery Beat (Time)* → `System`
*   **completed** → `archived` → *submit_report()* → `club_coordinator`

## 17. Data Flow Mapping

### Event Creation Flow
1.  **Frontend:** UI form collects Title, Date, type. Next.js triggers `POST /events`.
2.  **Network:** Axios interceptor injects `Authorization: Bearer <jwt>`.
3.  **Backend Middleware:** `get_current_user` extracts User ID 12. `require_roles` validates boolean.
4.  **Database:** SQLAlchemy inserts Event. Status becomes `draft`. Returns HTTP 200 + Event ID.
5.  **Response:** Next.js redirects to `/events/{id}/manage`.

### Approval Flow
1.  **Backend:** Dean requests `pending` via GET.
2.  **Action:** Dean sends `POST /approvals/{id}/action` with `{action: 'approved'}`.
3.  **Service:** `process_approval_action` intercepts. Updates event `updated_at`. Mutates status to `pending_director`.
4.  **SMTP Drop:** Pushes task into Celery queue for Director email notification.

### Report Upload Flow
1.  **Frontend:** Coordinator attaches 3 image files.
2.  **Backend:** FastAPI `UploadFile` loop processes buffer bytes. Uses `os.write` to HDD `<STORAGE_DIR>/reports/photos/`.
3.  **Submit Action:** Hits `POST /reports/{id}/submit`. Validates photos exist.
4.  **Database:** Event status flips `archived`. Report schema created.
5.  **Celery:** `generate_report_task` compiles Microsoft Word Document locally.

### Registration Flow
1.  **Frontend:** Student clicks `Register`.
2.  **Backend Validation:** Checks `event.status` == 'approved'. Checks `disable_student_registration`. Checks capacities.
3.  **Database:** Maps `event_id` and `student_id`.
4.  **Response:** 200 OK. Next.js flips button to `Cancel Booking`.

## 18. Failure & Recovery Handling

### Validation Failure (422)
*   **Failure:** Missing crucial parameter in JSON payload.
*   **Response:** FastAPI intercepts before executing method. Returns `422 Unprocessable Entity` detailed array mapping exactly what field failed.
*   **System Recovery:** Safe fallback to frontend form highlighting the bad inputs. No DB impact.

### API Logical Failure (40X)
*   **Failure:** Dean tries to approve an event that is actually `pending_director` (Double click glitch).
*   **Response:** `approval_service.py` evaluates state vs role requirements. Raises explicit `400 Bad Request: "Event is not pending Associate Dean review"`.
*   **System Recovery:** No data modified. Session rolls back safely. 

### Approval Process Fails (SMTP Drop)
*   **Failure:** `notify_director` fails because Gmail rejects SMTP bind due to invalid App Password.
*   **Response:** SMTP runs in a Celery background thread. Celery registers the crash. Event state transition in PostgreSQL (which ran synchronously) is maintained.
*   **System Recovery:** Event legitimately advances to `pending_director`. Celery will retry the email payload based on configuration parameters without blocking the HTTP request thread.

### File Upload Drop (Connection Reset)
*   **Failure:** Uploading a 5GB poster drops midway.
*   **System Recovery:** Chunk processing loops abort. File is truncated on disk. DB is not updated heavily. Next.js triggers failure notification.

### Database Timeout
*   **Failure:** PostgreSQL connection pool maxes out.
*   **Response:** HTTP 500 automatically unrolled via SQLAlchemy teardown. Data integrity preserved via `async_sessionmaker` automatic rollback on exception.

## 20. Hidden Constraints & Variables

### Approval Chain Reset Rules
*   **Non-Obvious:** A `Reject` or `Suggest Changes` forces the event back offline. Once resubmitted, the event does NOT resume where it left off. It completely resets back through `parallel_coordinator` (if applicable) and `associate_dean`.

### Visibility Override Masking
*   **Non-Obvious:** A student's visibility filter matches strictly via strings on `user.department.code` against `event.target_audience`. If an admin manually typed the audience with a typo, it breaks student accessibility forever without throwing a system error.

### Time-Based Logic Dependencies
*   **Non-Obvious:** Celery tasks run every 2 minutes. Therefore, an event transitioning to `ongoing` may lag by up to 119 seconds behind its official start time on the system clock. 
*   **Non-Obvious:** Registrations cannot occur when `status == ongoing` if `end_datetime` is passed. But until Celery picks it up to flag it `completed`, forms rely on frontend blockages to stop signups.

### System Settings Global Locks
*   **Non-Obvious:** `SystemSettings` table allows a `super_admin` to toggle `disable_student_registration=True`. This halts the entire university's ability to register across all events instantaneously without touching any individual event tables.

### Data Pagination Bounds
*   **Non-Obvious:** `limit` and `offset` structures are capped by backend variables bounded (e.g. `le=2000`). If a Coordinator generates 2001 attendees, their frontend lists truncate. They must rely on generated CSVs for full mapping safely.

## 21. Project File Structure & Code Interaction Map
> This section maps exactly how physical files in the repository correspond to logical processes. Use this map before modifying components to understand their downstream/upstream dependencies.

### A. Frontend Directory Layout (`Frontend/`)
Next.js 14+ App Router architecture.

*   `app/layout.tsx`: The root shell. Wraps the entire application in `<Providers>` (React Query / Contexts) and `<GlobalForceLogin>`. Any global states (like dark mode or universal auth locking) reside here.
*   `app/(auth)/`: Holds the authentication DOM routing.
*   `app/(dashboard)/`: The protected application core.
    *   **Interaction:** Relies heavily on `components/layout/SidebarLayout.tsx` which parses the JWT to dynamically render navigation options. Modifying dashboard files requires testing against multiple roles.
*   `components/Providers.tsx`: Houses the core frontend state management wrappers.
*   `components/layout/`: 
    *   `SidebarLayout.tsx`: The primary wrapper for all dashboard views. It dictates exactly which links a user can see (e.g., hiding Admin tools from Students).
    *   `TopNav.tsx` or similar: Handles the user profile dropdown and logout invocations.
*   `components/ui/`: Reusable atom-level UI components (Buttons, Modals, Inputs). Do not insert business logic here.
*   `store/` & `lib/`:
    *   Typically holds Zustand/Redux stores or Axios interceptors natively. The API interceptor attaches `Bearer <token>` to all outbound requests targeting the FastAPI backend.
*   `types/`: TypeScript definitions mapping cleanly mirroring Pydantic schemas from the backend. 

### B. Backend Directory Layout (`ems-backend/`)
FastAPI structured cleanly into domains.

*   **`main.py` (The Entrypoint)**
    *   Initializes the FastAPI application.
    *   Binds CORS middleware allowing the Next.js `Frontend/` port.
    *   Mounts all routers from the `routers/` directory sequentially.
*   **`app/auth/router.py` & `app/dependencies.py` (Gatekeepers)**
    *   `router.py` holds `/login`, yielding the `access_token`. 
    *   `dependencies.py` holds `get_current_user` and `require_roles`. **Interaction:** Almost every file in `routers/` imports `require_roles` to protect endpoints.
*   **`app/routers/` (Controllers)**
    *   *Interaction Rule:* Routers (like `events.py` or `dashboard.py`) handle I/O parsing, HTTP response casting, and role verification. They should NOT house immense business logic. They immediately invoke imports from `app/services/`.
*   **`app/services/` (Business Logic Engine)**
    *   `approval_service.py`: Contains the brain for status transitions.
    *   `venue_clash_service.py`: Used *by* routers before allowing a DB commit.
    *   `storage_service.py`: Writes `.img`/`.docx` buffers to the OS.
    *   *Interaction:* Services rely strictly on `app/models/` for table mapping and `app/schemas/` for shape verification.
*   **`app/models/` (DB Blueprints)**
    *   Declares the exact PostgreSQL schema via SQLAlchemy `Base`. E.g., `event.py`, `user.py`. 
    *   *Interaction Rule:* Used by `alembic` to generate migration scripts. Used by `services/` to query `async_sessionmaker`.
*   **`app/tasks/` (Celery Workers)**
    *   Files like `status_transitions.py` and `report_tasks.py`.
    *   *Interaction:* These files run completely parallel to FastAPI. They interact with the DB directly via a synchronous `create_engine` block. They do NOT pass through `routers/` or standard `dependencies.py` JWT logic.

### C. Live Code Interaction Scenario (Trace)
If tasked with changing how an "Event is Formatted":
1.  **Frontend Schema:** Update Next.js `types/event.ts`.
2.  **Frontend Component:** Update `components/events/EventCard.tsx` to display the new field.
3.  **Frontend Form:** Update `app/(dashboard)/events/create/page.tsx` payload construction.
4.  **Backend Schema:** Update `ems-backend/app/schemas/event.py` (Pydantic `EventCreate`).
5.  **Backend Model:** Update PostgreSQL `ems-backend/app/models/event.py` (SQLAlchemy `Column`).
6.  **Migration:** Run Alembic `alembic revision --autogenerate -m "Add Field"`.
7.  **Service Handling (Optional):** Update `routers/events.py` or `services/` if the field dictates new workflow routing.

### D. Centralized Rules of Modification
*   **Never bypass `services/`:** If an event status must change, do not type `event.status = 'approved'` inside `routers/events.py`. You must import and execute the dedicated method from `approval_service.py`.
*   **Never append async logic to synchronous operations:** `models` and `schemas` are synchronous definitions. Background workers in Celery parse synchronously, while FastAPI `routers` operate via `async def` and `awaitable` SQLAlchemy commands. mixing the engines will cause event looping locks.
